# Coupang Partners API 호출 제한 관측 보고서

작성 기준: 2026-09-02 KST

이 문서는 현재 저장소에 남아 있는 쿠팡 파트너스 API 산출물과 제한 테스트 로그를 비교한 것이다. DB에는 새로 저장하지 않았고, 이 보고서는 기존 로컬 파일과 `logs` 디렉터리의 JSONL 로그만 근거로 작성했다.

## 핵심 결론

2026-08-26에는 쿠팡 파트너스 Search API로 100개 키워드를 모두 성공 조회했고, 총 994개 상품 row를 만들었다. 이때 실제 평균 호출 속도는 약 0.805 req/sec, 48.32 RPM이었다.

2026-09-02 제한 테스트에서는 Search API를 약 2.0 req/sec, 120 RPM 속도로 호출했고, 52번째 호출에서 HTTP 200 + `rCode=403`이 발생했다. 응답 메시지는 `검색 API의 시간당 사용 횟수 ... 초과`였고, 재시도 가능 시각으로 2026-09-03 오후 5시 46분 28초 이후를 반환했다.

이후 2026-09-02 오후 9시 7분 16초에 Best Category API를 1회만 확인했을 때도 HTTP 200 + `rCode=403`과 같은 시간당 제한 메시지가 반환됐다. 따라서 Search API와 Best Category API는 독립 쿼터가 아니라 같은 상품 검색 계열 쿼터를 공유하는 것으로 강하게 보인다.

## 2026-08-26 당시 호출 속도

요약 파일 기준으로 계산하면 다음과 같다.

| 항목 | 값 |
|---|---:|
| 호출 수 | 100회 |
| 총 실행 시간 | 124.161초 |
| 실제 평균 초당 호출량 | 0.805 req/sec |
| 실제 평균 분당 호출량 | 48.32 RPM |
| 성공 수 | 100회 |
| 실패 수 | 0회 |
| 최초 제한 시점 | 없음 |
| HTTP 상태코드 | 제한 없음 |
| rCode/rMessage | 제한 없음 |

당시 설정 파일에는 `requests_per_minute: 40`이 들어 있었다. 그런데 실제 평균이 48.32 RPM으로 보이는 이유는 현재/당시 `RateLimiter`가 균등 간격 방식이 아니라 rolling window + burst 허용 방식이기 때문이다.

즉, `max_calls=40, period_seconds=60`이면 모든 호출을 1.5초마다 고르게 보내는 방식이 아니다. 처음 40개는 빠르게 나갈 수 있고, 60초 창이 차면 가장 오래된 호출이 만료될 때까지 대기한다. 그래서 짧은 전체 실행 구간에서는 평균 RPM이 설정값보다 높게 보일 수 있다.

당시 관측 결과만 보면 100회 호출까지는 제한이 발생하지 않았다. 다만 이 결과만으로 “항상 48 RPM이 안전하다”고 확정할 수는 없다.

## 왜 8월 26일에는 됐는데 지금은 막히는가

현재 파일과 로그만으로 원인을 하나로 확정할 수는 없다. 가능한 해석은 아래와 같다.

1. 2026-08-26 당시에는 해당 계정/API 키가 100회 Search 호출을 허용했다.
2. 2026-09-02 테스트 시점에는 더 낮거나 다른 형태의 시간당 제한이 적용됐다.
3. 2026-09-02 제한 테스트는 약 120 RPM으로 매우 빠르게 시작했기 때문에, 시간당 제한뿐 아니라 짧은 시간 내 과도 호출 패턴이 제한 트리거에 영향을 줬을 수 있다.
4. 제한 메시지는 단순히 “분당 제한”이 아니라 “시간당 사용 횟수 초과”라고 말한다.
5. 제한 발생 후에도 과거 프로브 스크립트가 `rCode=403`을 제대로 limit으로 인식하지 못해서 397회나 더 호출했다. 이 때문에 초과 카운트가 올라갔고, 이후 Best Category 확인 때 `현재 *2*회 초과`가 반환됐다.

- 2026-09-02 Search 테스트는 52번째 호출에서 HTTP 200 + `rCode=403`으로 제한이 발생했다.
- 제한 메시지는 `검색 API의 시간당 사용 횟수 초과`였다.
- 쿠팡 응답은 재시도 가능 시각으로 2026-09-03 오후 5시 46분 28초 이후를 반환했다.
- Best Category API도 Search 제한 상태에서 1회 호출 시 HTTP 200 + `rCode=403`을 반환했다.

### 2. 테스트로 추정한 값

- Search API와 Best Category API는 같은 상품 검색 계열 쿼터를 공유하는 것으로 보인다.
- 120 RPM은 현재 계정 상태에서 위험하다.
- 2026-08-26에 성공했던 48.32 RPM도 현재 안전값으로 그대로 쓰기 어렵다.
- 제한 발생 시 거의 24시간 쿨다운처럼 동작한다.
- 현재 운영은 전체 상품 API 합산 6 calls/hour 이하로 시작하는 것이 보수적이다.

### 3. 공식 문서 또는 외부 자료에만 있는 값

- 이 보고서에서는 공식 문서의 시간당/일일 한도를 확정값으로 쓰지 않았다.
- `시간당 10회` 같은 값은 이번 로컬 실측만으로 확정되지 않았다.
- 공식 일일 한도는 확인되지 않았으므로 하루 최대 호출량은 확정할 수 없다.
